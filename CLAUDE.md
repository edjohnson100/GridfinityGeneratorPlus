# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**GridfinityGeneratorPlus** — a fork of LevMishin's `GridfinityGenerator` Fusion 360 add-in (Python) that generates parametric [Gridfinity](https://gridfinity.xyz/) storage bins and baseplates directly inside Autodesk Fusion 360. This fork's distinguishing feature is a persistent, dockable HTML palette UI (`adsk.core.Palettes`) replacing the original's `CommandDialog`-based UI. It follows Autodesk's standard Fusion 360 add-in template layout (`lib/fusion360utils/` is unmodified Autodesk boilerplate — leave it alone unless fixing a genuine framework bug).

There is no build system, package manager, linter, or test suite in this repo — it only runs inside Fusion 360's embedded Python interpreter via the Fusion 360 add-in loader. There are no `requirements.txt`/`pyproject.toml`. The repo is tracked in git and hosted as a private GitHub repository (`edjohnson100/GridfinityGeneratorPlus`, `main` branch).

See `docs/Dev_Notes.md` for a running log of notable feature work and design decisions made in this fork (session-by-session notes, not auto-generated — update it when you finish a notable change).

`config.py`'s `ADDIN_NAME` (`'GridfinityGeneratorPlus'`) and `COMPANY_NAME` (`'LevMishin'`) are combined to build unique Fusion command/palette IDs — `ADDIN_NAME` was deliberately changed from the upstream `'GridfinityGenerator'` so this fork can be installed and run side-by-side with the original add-in without ID collisions.

## Running / testing changes

There is no CLI entry point or headless test runner — `adsk.core` / `adsk.fusion` are Fusion 360's runtime API modules and only exist inside the Fusion 360 process. To verify a change:

1. Open Fusion 360 → Utilities → Add-Ins → Scripts and Add-Ins → add this folder as an add-in (or point Fusion at `GridfinityGeneratorPlus.manifest`).
2. Run/reload the add-in, then use the "GridfinityGeneratorPlus" toolbar button (Solid Create panel) to open the palette and exercise the change interactively.
3. Use `futil.log(...)` (see `lib/fusion360utils/general_utils.py`) to write to the Fusion 360 Text Command window / console for debugging; toggle verbose logging via `config.DEBUG` in `config.py`.

Since there's no automated test suite, manually generate a bin/baseplate with the changed inputs and confirm the resulting solid body is correct in the Fusion 360 viewport before considering a change done.

## Architecture

### Add-in bootstrap
- `GridfinityGeneratorPlus.py` is the add-in entry point Fusion 360 calls (`run(context)` / `stop(context)`), delegating to `commands.start()` / `commands.stop()`.
- `commands/__init__.py` is the registry of top-level commands.
- `config.py` holds add-in-wide constants (`DEBUG` flag, `ADDIN_NAME`, `COMPANY_NAME`, `PALETTE_ID`).

### Commands (`commands/`) — mid-migration state, read carefully

This repo is **mid-migration** from a two-`CommandDialog` UI to a single persistent HTML palette UI. Both old and new command packages currently coexist on disk:

- **`commandGridfinityPalette/`** — the active, current UI. A single palette (`adsk.core.Palettes`), tab-switched between "Bin", "Baseplate", "Grid Optimizer", and "Theme", plus an always-visible "Common settings" panel above the tabs (shared fields: `baseWidthUnit`, `baseLengthUnit`, `xyClearance`, `magnetDiameter`, `magnetDepth`), with explicit "Update Preview"/"Generate"/"Clear Preview" buttons for Bin/Baseplate (no always-on live preview). The Grid Optimizer tab is a pure-Python advisory calculator (no `adsk.fusion` geometry, no preview/generate) that recommends a custom Gridfinity grid pitch for a user-entered list of drawer/cabinet openings, with half-bin credit and a width/depth priority weighting — see `optimizer.py` below. The Theme tab is pure client-side CSS (no Python geometry or validation involvement beyond persisting the selection) — see `resources/palette/style.css` below. `commands/__init__.py` registers only this command now — the old two are no longer wired up to run, just not yet deleted from disk. Structure:
  - `entry.py` — palette lifecycle: `start()`/`stop()`, `open_palette()`, `HTMLEventHandler` (dispatches JS→Python actions: `get_defaults`, `validate`, `update_preview`, `generate`, `clear_preview`, `edit_active_component`, `update_common`, `save_as`/`update_current`/`load`/`delete` (config manager, generic across all three tabs via `DEFAULTS_BY_TAB`/`VALIDATE_BY_TAB`), `factory_reset`, `optimize` (Grid Optimizer tab only — runs `optimizer.compute_best_fit()` and replies with `optimizer_result`, no preview/generate/geometry involved), `update_theme`, `save_imported_theme`, `remove_imported_theme`, `export_theme` (opens a native Fusion Save dialog defaulted to `resources/themes/` — see Theming below), `PaletteCloseHandler`, `_ensure_safe_to_mutate()` modal-safety guard. `_handle_edit_active_component()` implements re-edit/redo: it reads `Design.activeComponent` (the user hovers over a component in the browser and clicks the radio button that appears to its right to activate it first), looks up the `formJson`/`kind` custom attributes `generation.create_and_build()` stamps on every Hybrid-design-intent component it creates, repopulates the palette from that JSON, and adopts the existing `Occurrence` into `previewState` (`adopted=True`) so the existing Update Preview / Generate / Clear Preview flows transparently edit-in-place, rebuild, or delete it. It first checks whether the activated component is actually the *current, not-yet-finalized* preview itself (tracked, non-adopted) and bails with a toast instead of proceeding — `previewState.clear_preview(force=False)` only preserves *adopted* components, so adopting a fresh preview here would delete it out from under itself and crash on the now-deleted `Component`. `_ensure_hybrid_design_intent()` hard-blocks the `generate` action (not `update_preview`) when `Design.designIntent` isn't Hybrid — this is deliberate, not just an artifact of re-edit's requirements: settings living on the component as a component attribute (surviving save/share/reopen) is the add-in's core value proposition, so Generate refuses to produce a permanent component that can't carry that. Checked at Generate time rather than once on palette open, since the palette stays open across document tabs and the user could switch from a Hybrid to a Part/Assembly design mid-session. Preview is intentionally left unrestricted (still builds loose root-component features in Part/Assembly documents, same as before) since nothing permanent or attribute-bearing is at stake there.
  - **Grouped Undo**: Fusion has no Revit-style `Design.startTransactionGroup()`/`assimilate()` API for scripts/add-ins — confirmed via Autodesk's own docs that the only way to bundle several API calls into a single Undo entry outside of a command dialog is to run them from a headless command's `execute` event handler (everything done there is automatically one undo transaction). `_handle_update_preview`/`_handle_generate` run their clear-preview-then-build logic through `_run_grouped(work, name)`, which stashes the callable and `.execute()`s a hidden, never-shown `UNDO_GROUP_CMD_ID` command definition (registered in `start()`, no dialog inputs so Fusion auto-executes it immediately — same pattern as the palette's own toolbar button in `command_created()`); `name` retargets the hidden command definition's `.name` just before each execute so the Undo dropdown shows a real label instead of a generic one.
  - **Undo/Redo-aware preview tracking**: `previewState` is otherwise unaware of Fusion's own Undo/Redo mutating the document out from under it. `_on_command_terminated` (wired to `ui.commandTerminated`, deliberately *not* filtered to a specific `commandId` — the keyboard shortcut and the toolbar Undo arrow report different values) calls `previewState.resync()` after every completed command and pushes a fresh `preview_status` if it changed anything, so the Clear Preview button stays accurate through arbitrary Undo/Redo sequences.
  - `generation.py` — `create_and_build(kind, form)` / `build_bin(...)` / `build_baseplate(...)`, ported near-verbatim from the old dialogs' `generateBin`/`generateBaseplate`, now driven by plain form dicts instead of `CommandInputs`. Also stamps the originating `form` (as JSON, plus a `kind` marker) as custom attributes on the created component when building in Hybrid design intent — this is what makes `entry._handle_edit_active_component()` possible.
  - `validation.py` — `validate_bin(form)` / `validate_baseplate(form)` → `{valid, fieldErrors, computed}`, ported from the old dialogs' range checks. The `common` pseudo-tab has no direct entry in `VALIDATE_BY_TAB` — it's validated indirectly as part of whichever real tab (`bin`/`baseplate`) is active.
  - `previewState.py` — single-slot preview tracker (module-level state re-resolved via `Design.findEntityByToken`, supporting both a new Occurrence and a list of root-component timeline features); `track_preview(tab, tracked, adopted=False, original_name=None)`/`clear_preview(force=True)`/`has_preview()`. Only one preview component exists at a time across both tabs; the palette's "Clear Preview" button calls `clear_preview()` directly (default `force=True`, so it always deletes). The `adopted`/`force` pair exists for the "edit an already-generated component" flow: an *adopted* component (loaded via `edit_active_component`) is only actually deleted when `force=True` (an explicit Clear Preview / Update Preview / Generate click) — implicit paths (`PaletteCloseHandler`, add-in `stop()`) call `clear_preview(force=False)`, which just releases tracking and leaves the real component untouched, so closing the palette mid-edit never silently deletes work. Every not-yet-finalized component (fresh previews built with `generation.create_and_build(..., is_preview=True)`, and adopted components for the duration of an edit) is visually marked with a `PREVIEW_` name prefix (`generation.PREVIEW_NAME_PREFIX`) so it reads as unfinalized in the Fusion browser tree, not just in the palette UI — `Component.opacity` was tried for a "ghost body" look too but had no visible effect in practice, so it was dropped; name-prefix only. `original_name` on `track_preview` is the adopted component's pre-edit name, restored by `clear_preview(force=False)` if editing is released without being finalized or deleted — fresh previews don't need this since they're simply deleted outright. `resync()` reconciles this tracking against Fusion's Undo/Redo (see `entry._on_command_terminated` above): every preview ever tracked this session is kept in a bounded (`_PREVIEW_HISTORY_LIMIT = 50`) `_preview_history` list rather than overwritten, so if the currently-tracked entity was undone away, `resync()` can search backward through that history for an *earlier* preview that's reappeared — not just the single most-recently-cleared one — and re-adopt it.
  - `binInputState.py` / `baseplateInputState.py` — typed dataclasses (`from_form(dict)`) sitting between the raw JS form dict and the `*GeneratorInput` objects in `lib/gridfinityUtils/`.
  - `optimizer.py` — pure-Python fit/waste math for the Grid Optimizer tab (`calculate_fit`, `run_optimization`, `compute_best_fit`), ported from a standalone reference script the add-in doesn't otherwise use. No `adsk` imports. `run_optimization` ranks candidate grid sizes by a priority-weighted score (`PRIORITY_WEIGHTS`: `widthOnly`/`width`/`balanced`/`depth`/`depthOnly`) but still reports the actual unweighted leftover mm for display. `optimizerInputState.py` is the `from_form(dict)` dataclass counterpart (`OptimizerInputState`/`DimensionItem`), feeding `optimizer.compute_best_fit` directly instead of a `*GeneratorInput`/`generation.create_and_build`.
  - **Sortable dimensions table**: clicking a column header (Description/Width/Depth) in the Grid Optimizer's dimensions table sorts the rows (`script.js`'s `optimizerSort` state, click again to reverse), with newly-added rows respecting the active sort. This is a pure front-end reorder with no new persistence format — `readOptimizerItemsFromDom()` already reads `items` straight off the DOM in its current order for every validate/Calculate/save-config call, so the sorted order is simply whatever gets saved, no python-side changes needed. The sort indicator resets (but the row order doesn't) whenever a different saved set is loaded, since that set's saved order isn't necessarily sorted by whichever column was last clicked in this session.
  - `commandConfig/config.ini`, `commandConfig/ui_defaults.json` (`{"bin": {"activeConfig": ...}, "baseplate": {"activeConfig": ...}, "optimizer": {"activeConfig": ...}}`), `commandConfig/common.json` (live shared-field values, not tied to a named preset), `commandConfig/presets/{bin,baseplate,optimizer}/*.json` — file-per-named-config storage backing the palette's config manager (Save As / Update Current / Load / Delete per tab, plus per-tab and per-common Factory Reset — Bin's/Baseplate's Factory Reset also resets Common (and vice versa), since a stray Bin-only reset previously left a loaded 92mm preset's base unit stuck in Common with no indication why; Grid Optimizer's Factory Reset stays independent since it doesn't share Common fields; the Grid Optimizer tab's "Saved sets" section uses this same mechanism for named dimension lists). Bin/Baseplate presets snapshot the `COMMON_FIELDS` (`baseWidthUnit`, `baseLengthUnit`, `xyClearance`, `magnetDiameter`, `magnetDepth`) at save time (`TABS_WITH_SHARED_COMMON` in `entry.py`) and restore them into the live `common.json` on load, so a preset always reproduces the exact grid it was designed for — loading either tab's preset updates the one shared Common panel both tabs read from. The Optimizer tab's presets are still stripped of `COMMON_FIELDS` since it has no relationship to the physical grid.
  - `resources/palette/` — `index.html` / `style.css` / `script.js`, the actual palette UI. Field inputs use `id="{tab}.{fieldName}"` (`tab` is `bin`, `baseplate`, `optimizer`, `theme`, or `common`). `script.js` owns mm↔cm display conversion (Python/Fusion internal unit is cm) via a per-tab `MM_FIELDS` allowlist (including a `common` key), bridges to Python via `window.adsk.fusionSendData` / `window.fusionJavaScriptHandler.handle`, and never uses `localStorage` (all durable state is Python-owned JSON pushed via a `set_state` message). Field-change validation is debounced per-tab (`validateDebounceTimers`, keyed by tab — do not collapse back into a single shared timer, that previously caused validation for one tab to silently get cancelled by a validation request for another tab firing within the same 200ms window). Both `index.html`'s `script.js`/`style.css` `?v=N` query strings *and* `entry.PALETTE_VERSION` (the outer palette URL's own `?v=`) need bumping whenever their respective files change — Fusion can cache the palette webview by URL, so `PALETTE_VERSION` specifically must change whenever `index.html`'s markup changes, not just when `script.js`/`style.css` do.
  - **Modal component**: the palette's first real dialog UI (`#modal-overlay` in `index.html`, new theme-token-driven CSS, `script.js`'s `showConfirmModal`/`showPromptModal`/`showPickerModal`, all Promise-based on top of a generic `_openModal`/`_closeModal`) — replaces every native `window.confirm`/`window.prompt` call in the palette (there is no `window.alert`/`confirm`/`prompt` left anywhere in `script.js`). Supports Escape-to-cancel, Enter-to-confirm, a minimal Tab focus-trap, and restores focus to the triggering element on close. Only one modal can be open at a time by design (every call site `await`s it to completion before another user action could open a second one); `_openModal` defensively no-ops with a console error if that invariant is ever violated.
  - **Config manager UX**: per explicit user direction, **Update Current** is the only config-manager button that acts on the currently-active config directly (no dialog); **Load…**, **Delete…**, and **Save As…** each open a modal (`showPickerModal`/`showPromptModal`) instead of sharing an inline `<select>` the way they used to. `renderConfigStatus` (formerly `renderConfigManager`) now just renders a plain "Active config: **name**" status line and toggles Update Current's enabled state — `state.configs[tab]` (still populated via the existing `config_list` message) feeds the picker modals directly rather than a persistent dropdown.
  - **Cross-tab preview-replace warning**: `confirmPreviewReplace()` (in the generic `button[data-action]` click handler) warns via `showConfirmModal` before Update Preview/Generate on one tab would silently replace an unlocked preview currently tracked for the *other* tab — tied to those two buttons specifically, not to tab switching itself, since switching tabs to peek at settings and back should stay free. Driven by `state.previewTab`/`state.previewAdopted`, kept in sync from every `preview_status` message the palette receives (including the Undo/Redo resync path above).
  - **Second per-tab notification bars**: `showNotification()` mirrors every message into both the top `#notification` bar and a second `#{tab}-notification` bar local to whichever tab is active (positioned just above that tab's Configurations/Saved sets section, each with its own independent auto-hide timer) — added because a sufficiently tall palette (e.g. `body`'s `min-height` set high enough to fill a 4K display in dark themes) can scroll the top bar out of view long before the Generate/config buttons near the bottom.
  - **Theming**: `style.css` follows the "Theme Designer Pro" standard (the integration guide describing it lives in `Archive/` — a personal, cross-project reference doc, not specific to this repo, so it's kept out of the public tree) — every themeable value is a `var(--name)` custom property, `:root` holds the default ("Light") values, and `:root[data-theme="Name"]` blocks (`Dark`, `Midnight`, `Sandstone`) override them; switching is `document.documentElement.setAttribute('data-theme', name)` / `removeAttribute` (must target `<html>`, not `<body>` — `:root` in CSS only ever matches `<html>`). The Theme tab is intentionally NOT wired through the generic `MM_FIELDS`/`requestValidation`/config-manager machinery the other tabs share (there's nothing to validate or version) — `onSetState` special-cases `tab === 'theme'` in `script.js` to call `applyTheme()` instead. Persistence is split across two files at the repo root (both gitignored — per-machine state): `lib/appConfig.py`'s `GGPlus_config.json` (same file/pattern as palette window geometry) remembers the currently-*active* theme's name **plus** `fontFamily`/`fontSize` via a dedicated `update_theme` action, while `appConfig.load_imported_themes()`/`save_imported_theme()`/`delete_imported_theme()` maintain a separate `imported_themes.json` (`{themeId: varsDict, ...}`, one entry per theme ever imported, via `save_imported_theme`/`remove_imported_theme` actions) so switching back to a previously-imported-but-not-currently-active theme still works after a restart — `get_defaults` sends the whole imported-themes dict alongside the active theme's name so `script.js` can repopulate the dropdown and its in-memory `importedThemes` cache in one shot. A `System` option (the default) watches `matchMedia('(prefers-color-scheme: dark)')` client-side to preserve the pre-Theme-tab automatic OS dark-mode behavior. Users can import a `.theme.json` (Theme Designer Pro's export format, `{id, vars}`, see the sample files at `resources/themes/`) via a plain `<input type="file">` + `FileReader` read entirely client-side (no Python round-trip to read the file, only to persist the resulting id/vars) — injected as a dynamically-generated `<style id="dynamic-theme-overrides">` tag, per the integration guide's Step 5. Importing (or exporting) a `.theme.json` with an `id` matching an existing entry simply overwrites it — `save_imported_theme` was already an upsert, so there's no separate "remove before re-import" step needed for the "tweak a theme's font settings and re-export it" workflow.
  - **Theme font controls & export/remove**: Font Family (a 3-option `<select>` — Sans-serif/Serif/Monospace, deliberately not free-text or a long font list, per user request to keep it simple) and Base Font Size (px) are edited independently of *which* theme is selected, and apply on top of any of them (built-in or imported) via `applyFontOverrides()` — a separate `<style id="font-overrides">` tag setting plain `:root { --font-family: ...; --font-size-base: ...px; }`, distinct from `injectCustomTheme()`'s per-`data-theme`-name color overrides, so font settings aren't tied to a specific theme name. `THEME_VAR_NAMES` (kept manually in sync with `style.css`'s `:root` block) is colors-only and deliberately excludes `--font-family`/`--font-size-base` — it used to include them, but baking font into a theme's own `vars` let `:root[data-theme="X"]`'s higher CSS specificity silently win over the independent font-overrides `:root` block on import, so font never reliably round-tripped through export/import. **Export theme.json…** now sends `fontFamily`/`fontSize` as separate top-level fields (sourced from `state.forms.theme`, not `getComputedStyle`, to sidestep that same cascade ambiguity) alongside the colors-only `vars` snapshot, written by Python (`entry._handle_export_theme`) via a native `ui.createFileDialog()` Save dialog defaulted to `resources/themes/` — a plain client-side `Blob`/anchor-`download` was tried first but has no reliable destination inside Fusion's embedded webview (confirmed by user report: exported files were never found in the OS Downloads folder). Import reads the new top-level fields (falling back to the legacy `vars['--font-family']`/`vars['--font-size-base']` keys for older exports and the bundled `resources/themes/*.theme.json` samples, which still bake font in) and always strips those two keys back out of `vars` before persisting/injecting, so a legacy file self-heals into the new format the moment it's imported rather than re-triggering the specificity bug. **Remove imported theme** is disabled (`updateThemeRemoveButtonState()`) whenever the selected theme is one of the 5 built-ins or not present in `importedThemes`; only `body`'s base size actually scales via `var(--font-size-base)` today — most of the rest of the UI still uses fixed px font-sizes (`.field-hint`/`.field-error` are the one exception, using `0.92em` so they track the base size) — a deliberate scope call, not an oversight, revisit only if there's user feedback wanting more of the UI to scale.
  - **Design note on `hasMagnetCutouts`**: the boolean toggle stays per-tab (bin and baseplate each keep their own checkbox/gating) while only the physical size (`magnetDiameter`/`magnetDepth`) moved into the shared Common panel — a single shared toggle would conflict with Light-baseplate-type gating, which needs to disable baseplate's magnet toggle independently of bin's.
  - **Light baseplate type gating**: when `baseplate.plateType === 'Light'`, magnet cutouts and screw holes are disabled in the UI with an explanatory hint (mirroring the pre-existing `extraBottomThickness`/`hasConnectionHoles` gating) — this reflects real gating already present in `baseplateGenerator.py` (`hasExtendedBottom`/`hasSkeletonizedBottom`), not a new generator-side restriction.
  - **Dependent bin checkbox gating**: `updateBinConditionalVisibility()` also disables-and-unchecks `bin.withLipNotches` whenever `bin.withLip` is unchecked, and `bin.hasMagnetCutoutsTabs` whenever `bin.hasMagnetCutouts` is unchecked (re-enabling, but not auto-checking, on re-check) — both fields are meaningless without their parent, and this also self-heals an old saved config where the dependent field was checked without its parent, since the function runs from `writeFormToDom` on every load/render, not just on the parent's own `change` event.
- **`commandCreateBin/`**, **`commandCreateBaseplate/`** — the legacy `CommandDialog`-based commands (same shape: `entry.py` builds `CommandInputs`, `commandConfig/` holds `ui_input_defaults*.json`). No longer registered/reachable from `commands/__init__.py`. **Slated for deletion** once the new palette is verified working end-to-end in Fusion — not yet removed. Do not build new features on top of these.
- **`lib/ui/commandUiState.py`** — the `CommandUiState`/`SingleInputState` abstraction the legacy dialogs used to bind `CommandInput` widgets to persisted JSON. Unused by the palette UI. Also slated for deletion alongside the legacy commands above — check with the user before deleting; keep `lib/ui/unsupportedDesignTypeException.py` (still raised by `generation.py`).

When the legacy commands are eventually deleted, this section should be trimmed down to just the `commandGridfinityPalette/` description.

### Geometry generation (`lib/gridfinityUtils/`)
Unchanged by the palette migration — this is where the actual solid-body construction happens, using the Fusion 360 API (`adsk.fusion`) to build sketches, extrude/patch/pattern/shell/fillet features, and boolean-combine bodies. Key modules:
- `const.py` — all Gridfinity standard dimensions (wall thickness, clearances, base/lip heights, tab/scoop sizes, screw/magnet cutout sizes) as module-level constants in centimeters (Fusion 360's internal unit). Change these only to alter the physical Gridfinity spec defaults, not per-command behavior.
- `baseGenerator.py` / `baseGeneratorInput.py` — the Gridfinity "base" (the stacking foot profile shared by both bins and baseplates). `createSingleGridfinityBaseBody()` bakes the `xyClearance` gap directly into each per-cell sketch (`baseWidth/baseLength - xyClearance*2`, sketched coincident with the true origin — no offset dimension) and into that same cell's own corner fillet radius (`cornerFilletRadius - xyClearance`), matching the exact footprint/fillet the bin body wall (`binBodyGenerator.py`) already builds for itself. `createBaseBodyPattern()` then patterns these already-correctly-sized cells at the *unreduced* `baseWidth`/`baseLength` pitch, so adjacent cells naturally leave a small (`2×xyClearance`) gap between their feet — this is expected Gridfinity behavior (real bases have a gap between adjacent unit cells), not a defect. `cutBaseClearance()` — a separate, later whole-assembly clearance-cut pass — is no longer called by the palette (`commands/commandGridfinityPalette/generation.py`'s `build_bin`) since baking the clearance in from the start avoids the geometric mismatch between that pass's fillet/technique and the per-cell fillet that was producing a visible notch at every interior seam; the function itself is left defined and unchanged since the legacy `commandCreateBin/entry.py` still imports and calls it directly.
- `binBodyGenerator.py` / `binBodyGeneratorInput.py` — the bin's hollow/shelled/solid body, including `uniformCompartments` and compartment layout.
- `binBodyCutoutGenerator.py`, `binBodyLipGenerator.py`, `binBodyTabGenerator.py` (+ matching `*Input.py`) — bin sub-features: interior compartment cutouts, the stacking lip, and the pull/label tab.
- `baseplateGenerator.py` / `baseplateGeneratorInput.py` — the baseplate body.
- Low-level geometry helpers used across generators: `sketchUtils.py`, `shapeUtils.py`, `extrudeUtils.py`, `combineUtils.py` (boolean join/cut), `filletUtils.py`, `edgeUtils.py`, `faceUtils.py`, `shellUtils.py`, `geometryUtils.py`, `patternUtils.py`, `commonUtils.py`.

**Input-object pattern**: every generator function takes a corresponding `*GeneratorInput` object (e.g. `BaseGeneratorInput`, `BinBodyGeneratorInput`) rather than a long parameter list. These input classes use Python `@property`/setter pairs for every field (not plain attributes) and set sensible defaults from `const.py` in `__init__`. When extending a generator with a new parameter, add a property to its `*Input` class following the existing getter/setter boilerplate style, then thread it through the generator function and `commandGridfinityPalette/generation.py`.

**Units**: Fusion 360's internal length unit is centimeters — all dimension constants and geometry code work in cm. The palette's form dicts also carry cm values matching the `*GeneratorInput` fields directly; `script.js` is responsible for mm↔cm conversion for on-screen display only.

### Shared utilities (`lib/`)
- `lib/fusion360utils/` — Autodesk's own add-in template helpers (event handler registration/cleanup, logging, error handling). Treat as vendored framework code.
- `lib/configUtils.py` — generic `.ini` (via `configparser`) and JSON config read/write helpers.
- `lib/appConfig.py` — thin wrapper over `configUtils` for add-in-wide runtime settings not tied to any single command, stored in `GGPlus_config.json` at the repo root (gitignored — per-machine state, unlike the tracked `commandConfig/` presets). Currently holds the palette's remembered window geometry (`entry.py`'s `_save_palette_geometry`/`_load_palette_geometry`, keyed `paletteGeometry`: `width`, `height`, `left`, `top`, `dockingState`), captured on palette close (`PaletteCloseHandler`) and add-in `stop()` since Fusion's `Palette` has no move/resize event to hook live, plus the active theme (name/fontFamily/fontSize) and `load_imported_themes()`/`save_imported_theme()`/`delete_imported_theme()` for the separate `imported_themes.json` (see Theming above). Intended as the home for future add-in-wide defaults beyond the palette.
- `lib/ui/commandUiState.py` — legacy, see Commands section above.
- `lib/ui/unsupportedDesignTypeException.py` — raised when the active Fusion document isn't a supported design type (e.g. timeline disabled) for running a generator command.
