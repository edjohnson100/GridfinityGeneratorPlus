## 2026-07-21 — Shelled-bin crash and off-center baseplate cutouts (v1.2.1.0)

- **Bug 1 — Shelled bins crashed with `ASM_REM_NO_SOLUTION`**: `commandGridfinityPalette/generation.py::build_bin` shifted `baseGeneratorInput.originPoint` by `-xyClearance` in X/Y (added during the half-unit edge work below, intended to better center the bin's foot within the baseplate's cutout opening). `binBodyGenerator.createGridfinityBinBody`'s wall box was never given the same shift, so the foot and wall — one continuous physical surface — stopped being coincident. `combineFeatures`' boolean join (Hollow/Solid bins) silently absorbed the resulting non-coincident seam; `ShellFeatures.add()` did not, and threw `RuntimeError: 3 : Shell1 / Compute Failed // ASM_REM_NO_SOLUTION` on every Shelled bin. **Fix**: reverted the shift — `baseGeneratorInput.originPoint` is unshifted again, flush with the bin body.
- **Bug 2 — baseplate cutout openings off-center**: user found this visually (zoomed screenshot showing front/left wall-to-opening spacing ~0.5mm shorter than back/right) after confirming the reverted bin fix left bin/baseplate wall alignment itself perfect. Root cause was actually in `baseplateGenerator.py`, not the bin: both cutout blocks (`cutoutInput` for full center cells, `reducedCutoutInput` for half/quarter edge/corner cells) offset their `originPoint` by `-xyClearance * 2` from the nominal cell origin. The cutout is oversized by `xyClearance * 2` total (to leave `xyClearance` slack around a same-size foot on every side), so the correct origin offset to *center* that slack is `-xyClearance`, not `-xyClearance * 2` — the old offset left the opening shifted toward the front/left by a full `xyClearance`. **Fix**: both offsets corrected to `-xyClearance`. Confirmed by the user as dead-on after the fix, independent of Bug 1's fix.
- **Process note**: Bug 1's original shift was a reasonable-looking attempt to fix Bug 2's symptom (off-center opening) but fixed it on the wrong side of the interface (the bin's foot instead of the baseplate's opening), which is what broke the bin's own internal geometry instead. When a coordinate offset is added to fix how component A looks next to component B, check whether A's own internal consistency assumptions (here: foot flush with wall) still hold before assuming the fix is correct.
- **Version**: bumped `GridfinityGeneratorPlus.manifest`/`README.md`/palette footer to `1.2.1.0`, `PALETTE_VERSION` 24→25 (index.html markup text changed) — bug fixes only, PATCH bump per [[versioning-independent-from-upstream]].

## 2026-07-21 — Half-unit edge support for bins & baseplates (in-Fusion testing found & fixed 3 bugs, shipped as v1.2.0.0)

- **Feature**: new opt-in Left/Right/Front/Back half-unit checkboxes on both the Bin and Baseplate tabs. Checking an edge adds a half-unit-wide (e.g. 21mm for a 42mm grid) strip to that side; where two perpendicular checked edges meet at a corner, that corner cell is automatically quarter-size (half x half) — this falls out of the geometry model rather than being special-cased. Both tabs now also allow their core unit count to be `0` (e.g. a bin built purely from two half-unit strips, or even a single quarter-unit cell from one corner), when the relevant half-edge flag(s) supply the rest of that axis. User's motivating use case: a baseplate built as 1 full unit surrounded by half-units on all 4 sides, matched by a single bin built the same way instead of assembling 4 separate small bins.
- **Architecture — shared "grid slicing" model** (`lib/gridfinityUtils/gridSlicing.py`, new module, no `adsk` imports): for each axis, builds an ordered list of cell sizes (`[half if leading edge checked] + [full] * coreCount + [half if trailing edge checked]`), then decomposes the resulting 2D grid into up to 9 regions — 1 uniform center block (today's existing full-size grid, unchanged), 4 edge strips (1D patterns of half-size cells), and up to 4 individually-placed quarter-size corner cells. When no half-edges are checked, this degenerates to exactly the original single center region — zero behavior change for existing users/presets, confirmed via a standalone script run outside Fusion before wiring it in (`buildGridModel`/`enumerateGridRegions` have no Fusion dependency, so this was directly runnable).
- **`baseGenerator.createBaseBodyGrid()`** (new, alongside the existing `createBaseBodyPattern` which is left untouched for the legacy `commandCreateBin`): builds one native rectangular pattern per region instead of assuming a uniform grid. Distinguishes a cell's *drawn* size (which may be oversized by `xyClearance` for cutout-style cells, e.g. baseplate's cutout body) from the grid's *true* unit pitch (used for region positions and pattern spacing) via a fixed additive "oversize delta," so half/quarter cells get the same flat clearance margin as full cells rather than a proportionally scaled one.
- **Decision: magnet/screw cutouts never apply to non-full-size cells** — `BaseGeneratorInput.isReducedCell` (new flag) suppresses `createSingleGridfinityBaseBody`'s existing cutout gate regardless of `hasMagnetCutouts`/`hasScrewHoles`. Only true 1x1 cells (the center region) get the standard 4-hole pattern.
- **Latent off-origin bug found and fixed while building this**: `createSingleGridfinityBaseBody`'s internal magnet/screw-hole cutout logic (construction-plane offsets and the hole center point) assumed the cell's `originPoint` was always the global origin — true for every *existing* call site (a single seed cell always built at `(0,0)` before being patterned), but no longer true once a grid's center region can be shifted away from `(0,0)` by a leading half-edge. Fixed by making those offsets relative to `input.originPoint` instead of the global origin — a no-op for every pre-existing caller (`originPoint` was always `(0,0)` there), but required for the center region case here.
- **Baseplate** (`baseplateGenerator.py`): the existing single-cell-with-extras construction (skeletonized-bottom/magnet-groove/connection-hole sketch geometry) is kept exactly as-is and now guarded to run *only* when both core counts are `> 0`, applying only to the center region's one representative cell — half/quarter edge/corner cells are always plain, extras-free cutout bodies via `createBaseBodyGrid`. Connection holes stay scoped to the core grid only (no physical meaning on a half-width strip with no full-pitch neighbor) — an intentional scope limit, not a bug, revisit only on user feedback. The outer `binInterfaceBody` footprint and the connection-hole mirror planes now derive from the grid model's actual total size/center position instead of the old `coreCount * baseUnit` multiplication.
- **Bin** (`binBodyGenerator.py`, `binBodyLipGenerator.py`): bin body footprint switches from `baseWidth * binWidth` to the grid model's total size. Lip notches (decision: one notch per module, including half-width edge modules, not just full ones) reuse the same 9-region grid via `createBaseBodyGrid`, called with the exact same `GridModel` object the bin body already built (threaded through a new `gridModel` property on `BinBodyLipGeneratorInput`) so body and lip can never disagree about the grid shape.
- **Palette**: new `hasHalfLeft/Right/Front/Back` checkboxes on both tabs (generic `id="{tab}.{fieldName}"` binding picks them up with no `script.js` change needed for read/write). `validation.py` relaxes the `binWidth/plateWidth > 0` checks to allow `0` only when the relevant half-edge flag(s) cover that axis, and now populates `computed.totalWidthMm/totalLengthMm` for baseplate too (previously always an empty dict — a pre-existing gap this closes as a side effect). `script.js`'s `renderComputed` generalized from bin-only to accept a `tab` parameter, since baseplate now has its own computed-size display (`baseplate-computed-dimensions`) mirroring bin's.
- **Bug found in testing #1 — orphaned, un-cut magnet/screw cutout bodies on half/quarter cells**: the `isReducedCell` gate only wrapped the final join/4x-circular-pattern/cut-into-body step in `createSingleGridfinityBaseBody`, not the `shapeUtils.simpleCylinder()` calls that actually create the screw-hole/magnet-socket bodies (those were gated only by `hasScrewHoles`/`hasMagnetCutouts`). Result: a lone, never-patterned, never-subtracted cylinder body left floating in the component for every half/quarter cell when magnet cutouts were enabled — visible in a rendered preview as a single uncut hole outline in one corner of each reduced cell. Fixed by also requiring `not input.isReducedCell` on both of those top-level `if` checks, so no cutout body is created at all for non-full cells.
- **Bug found in testing #2 — skeletonized-bottom groove sketch broken for a shifted center cell**: `baseplateGenerator.py`'s "center bottom cutout" sketch (the 4x-rotated L-shaped groove carved into each full unit cell for the Skeletonized plate type) picked its near vertical/horizontal edges via `min(..., key=lambda x: abs(x.startSketchPoint.geometry.x))` — "nearest to sketch-local (0,0)" — and built the groove's inner corner via hardcoded `±(half-width - xyClearance)` absolute coordinates. Both assumed the cell always sits at the true origin, which stopped being true once a *leading* half-edge (Left or Front) shifts the center region away from `(0,0)` — confirmed empirically by the user: Right/Back-only (which never shift the center cell, since only a *leading* edge affects `centerRegion.originX/Y`) stayed correct, while Left/Front-only broke every core cell identically (only the un-rotated corner of the L-groove survived; the 3 rotated copies landed on a wrong axis). Fixed by anchoring edge selection to the screw-hole circle's own sketch position (already correctly placed via `modelToSketchSpace`, hence translation-invariant) instead of sketch `(0,0)`, and by computing the groove's inner corner from the actual measured cell width/height (`half-distance minus xyClearance`, preserving the original small structural web where the 4 rotated L-cutouts meet) instead of hardcoded absolute offsets. User confirmed this fully resolved it for single-edge and all-4-edges cases, with results matching the non-half-edge baseline.
- **Accepted design compromise, confirmed by user**: half/quarter edge/corner cells on a Skeletonized baseplate stay solid (no groove skeletonization), same as a Full-type cell — only true 1x1 center cells get the L-groove pattern. Not pursued further since the groove's corner geometry scales with magnet/screw diameter, making a reliable half/quarter-size version more complex than the payoff justifies; user explicitly signed off on this as acceptable.
- **Also found and fixed during this same testing pass**: bin foot/base sketches (built via the same `createBaseBodyGrid` path) were flush at the true origin while baseplate cutout openings are drawn shifted by `-2×xyClearance` at unshrunk width, so each bin foot sat `xyClearance` off-center within its baseplate grid opening. Fixed in `commands/commandGridfinityPalette/generation.py::build_bin` by shifting `baseGeneratorInput.originPoint` (feet only, not the bin body) by `-xyClearance` in X/Y — applies uniformly to every region via the same additive-offset mechanism, so it fixes full/half/quarter cells alike. This one predates the half-unit work (it affects plain full-size bins too) but only surfaced once half-size testing prompted closer alignment checking.
- **Status**: user has now tested magnet cutouts + half/quarter cells (fixed), Skeletonized + half-edges (fixed, with the solid-half-cells compromise accepted), and bin/baseplate foot alignment (fixed).
- **Version**: bumped `GridfinityGeneratorPlus.manifest`/`README.md` to `1.2.0.0` alongside the DXF-ready sketch feature below (new backward-compatible features, no breaking changes — MINOR bump per [[versioning-independent-from-upstream]]).

## 2026-07-21 — DXF-ready sketch for laser-cut baseplates

- **Feature**: new opt-in "Generate DXF-ready sketch" checkbox on the Baseplate tab (`baseplateGeneratorInput.generateDxfSketch`, all `plateType`s). The user's use case: laser-cutting baseplates out of thin sheet material (e.g. gluing up two 3mm layers, mixing Light/Skeletonized/Full) instead of/alongside 3D printing. The add-in only produces the sketch — no DXF/SVG file export code — so the user can export it by hand with whichever tool they prefer.
- **Technique, specified directly by the user from hands-on Fusion experience** (not derived from reading the generator code): right after "Final baseplate cut," build a construction plane at the plate's mid-height, add a sketch on it, and use Fusion's Project/Include → Intersect tool against the single baseplate body with the projection link enabled — this is `Sketch.projectCutEdges(entity)` in the API.
- **Shared midplane**: the mid-height construction plane the DXF step needs is the exact same one the existing Stackable plate type already built for its own split/mirror step (previously created only inside `if input.isStackable:`). Moved that construction out to run unconditionally right after the final cut, renamed from `"Baseplate stack split plane"` to `"Baseplate midplane"` since it's no longer stack-specific, and both the DXF sketch and the Stackable split/mirror logic now reference the one plane instead of each building their own.
- **API signature gotcha**: first pass called `projectCutEdges(binInterfaceBody, True)`, assuming a second boolean argument for "linked" (mirroring the Fusion UI's Intersect tool having a Link checkbox) — this raised `TypeError: takes 2 positional arguments but 3 were given` the first time the user actually ran it. `projectCutEdges()` takes only the entity; the projection is automatically associative, not a toggle. Fixed to `projectCutEdges(binInterfaceBody)`.
- **Scope**: enabled for all four baseplate types for now (not gated by `plateType`), even though the user has only manually verified Light and Stackable so far — Full and Skeletonized are untested pending the user's own follow-up, and the option may be narrowed later if those don't work.
- **Version**: bumped alongside the half-unit edge support work above, to `1.2.0.0` (MINOR bump per [[versioning-independent-from-upstream]]).

## 2026-07-20 — v1.1.2 hotfix: stacked baseplates tripled on export

- **Bug**: user generated a Stackable baseplate with Stack Count = 2, which looked correct in the Fusion viewport, but exporting/slicing it produced 3 copies of every body instead of the expected 2 baseplates + 1 interface layer. The extra bodies were exactly coincident with the real ones in the viewport (same position, same shape), so nothing looked wrong until the browser tree was expanded or the file was sliced — the user found the actual root cause themselves by inspecting the Fusion timeline directly rather than reasoning from the generator code, and located it precisely: both rectangular pattern features backing the stack (`Baseplate` and `Interface` copies) had Axis 1's quantity set correctly (matching Stack Count) but Axis 2's quantity left at Fusion's default of 3.
- **Root cause**: `patternUtils.linearPattern()` (`lib/gridfinityUtils/patternUtils.py`) is a single-axis wrapper around `rectangularPatternFeatures.createInput()`, used by the Stackable baseplate's stack-copy step (`baseplateGenerator.py`, patterning both the baseplate body and the interface-layer spacer body when Stack Count > 1). `createInput()` only configures direction one; Fusion's `RectangularPatternInput` keeps its own default direction-two quantity (3) active even when `directionTwoEntity` is never set, so every pattern built through this helper was silently tripled in an unused second direction. This is distinct from every other rectangular-pattern call site in the codebase (`baseGenerator.createBaseBodyPattern`, `baseplateGenerator.py`'s main cell pattern, `binBodyLipGenerator.py`'s lip notches) — those are genuine 2D patterns and already set `directionTwoEntity`/`quantityTwo` explicitly, so they were never affected.
- **Fix**: `linearPattern()` now explicitly sets `patternInput.quantityTwo = ValueInput.createByReal(1)` right after `createInput()`, with a comment flagging the gotcha for any future single-axis pattern helper. One-line fix, no other files changed. Any Stackable baseplate generated before this fix should be regenerated.
- **Version**: bumped `GridfinityGeneratorPlus.manifest`/`README.md` to `1.1.2.0` (bug fix only — PATCH bump per [[versioning-independent-from-upstream]]).

## 2026-07-20 — v1.1.1: bin base bottom-edge notch fix, dependent checkbox gating

- **Bin base bottom-edge notch, root cause and fix**: user reported (with screenshots) a small notch in the outer bottom edge of multi-cell bins at every interior 42mm grid seam. First investigated this as a per-cell-vs-whole-footprint corner-fillet problem and built a two-session "Bin Generator: Standard vs Rebuilt-compatible" mode — a new `baseGeneratorRebuilt.py` splitting the base into a per-cell tapered "foot" and a whole-footprint flat "bridge" slab, modeled on the vendored `gridfinity-rebuilt` OpenSCAD project's technique (`Archive/gridfinity-rebuilt-openscad-main/src/core/base.scad`'s `gridfinityBase()`/`_base_bridge_solid()`). Two implementation passes on this approach still didn't produce correct geometry (wrong taper shape, ~1.2-2.15mm short of the real Gridfinity spec height) even after clarifying the exact 2.15mm/1.8mm/0.8mm chamfer/straight/chamfer profile with the user. The user then found the *actual* root cause by editing the Fusion timeline directly on a real generated bin (not by reasoning about the generator code): the base is built in two separate, geometrically inconsistent passes — `createSingleGridfinityBaseBody()` sketches one unit cell at full width with the full (unreduced) corner fillet radius, pre-shifted by `-xyClearance`; then a later `cutBaseClearance()` reshapes the *entire assembled* multi-cell footprint using a *different* fillet radius and an entirely different sketch/offset/cut technique. Those two independent operations don't perfectly agree at the boundary between a per-cell fillet and the assembly-wide clearance cut, producing the notch. The user's tested fix: bake the exact same end state directly into the original per-cell sketch instead — `actual_base_width/length = baseWidth/baseLength - xyClearance*2` (confirmed this needs to be the *doubled* clearance, not a single one, to exactly match `binBodyGenerator.py`'s existing wall-body footprint formula, which is also flush-at-origin and shrunk by `2×xyClearance` total) and `cornerFilletRadius - xyClearance` for the per-cell fillet (a single reduction, matching the old `cutBaseClearance`'s own formula) — with the sketch's start point no longer pre-shifted, so it lands exactly on the sketch's own origin and gets a coincident constraint instead of a distance dimension. This eliminates the entire second pass: `cutBaseClearance()` is no longer called from the palette's `generation.build_bin`, though the function itself is left defined and unchanged in `baseGenerator.py` since the legacy, unregistered `commandCreateBin/entry.py` still imports and calls it directly. Net result: a **smaller, more surgical fix** than the abandoned Rebuilt-compatible mode — 2 lines changed in `baseGenerator.py`, a handful in `generation.py`, nothing else. All of the Rebuilt-compatible work (new module, new `const.py` values, new UI selector) was fully reverted (`git restore` + deleting the new file) before this fix was written. The remaining small (`2×xyClearance`) gap now visible between adjacent unit cells' feet is expected/spec-accurate Gridfinity behavior, not a defect — confirmed against a real gridfinity-rebuilt web-renderer screenshot the user supplied, which shows the same gap.
- **Dependent checkbox gating**: user tested every bin option after the fix above and found two UX gaps — **With lip notches** and **Add magnet cutout tabs** could be left checked while their parent option (**With lip** / **Add magnet cutouts**) was unchecked, which is meaningless. `script.js`'s `updateBinConditionalVisibility()` now disables and force-unchecks each dependent checkbox whenever its parent is unchecked, and re-enables (without auto-checking) it when the parent is checked again — new `change` listeners on `bin.withLip`/`bin.hasMagnetCutouts`, plus `.disabled-row` extended in `style.css` to apply directly to a label element (not just its descendants), since these are single-checkbox rows rather than the multi-field fieldsets the existing pattern (Light baseplate gating) was built for. Since this runs from the same function `writeFormToDom` already calls on every load/render, it also self-heals any old saved config where a dependent field was checked without its parent.

## 2026-07-18 — Theme export via native Save dialog + font round-trip fix, linked Factory Reset, sortable Grid Optimizer table, "document attribute" → "component attribute" terminology fix

- **Theme export went to a native Save dialog**: user reported exporting a theme twice and finding it in neither `resources/themes/` nor the OS Downloads folder. Root cause: `script.js`'s Export button built a `Blob` + anchor `download` client-side, which has no reliable/discoverable destination inside Fusion's embedded webview. Replaced with a Python round-trip (`export_theme` action → `entry._handle_export_theme`) that opens a real `ui.createFileDialog()` Save dialog defaulted to `resources/themes/`.
- **Font Family/Size didn't survive export → import**: while fixing the above, traced a second, previously-unreported bug — `THEME_VAR_NAMES` (the list of CSS vars snapshotted on export) included `--font-family`/`--font-size-base` alongside colors, all flattened into one `vars` object that gets injected as `:root[data-theme="X"]`. But the independent Font Family/Size controls apply as a separate, lower-specificity plain `:root {...}` override (`applyFontOverrides`) — since an attribute selector (`:root[data-theme="X"]`) is always more CSS-specific than plain `:root`, an imported theme's baked-in font silently won every time, while the import code path never updated the Font Family/Size dropdown/input or the persisted active-theme config to match, so the two drifted out of sync. Presented the user two fix options (font as theme-owned vs. font as fully independent); user chose independent. `THEME_VAR_NAMES` is now colors-only; export sends `fontFamily`/`fontSize` as separate top-level JSON fields sourced from `state.forms.theme` (not `getComputedStyle`, to avoid the same cascade ambiguity); import reads those fields (falling back to the legacy `vars` keys for older exports and the bundled `resources/themes/*.theme.json` samples, which still bake font in) and always strips `--font-family`/`--font-size-base` back out of `vars` before persisting/injecting, so legacy files self-heal into the new format the moment they're imported.
- **Factory Reset didn't actually reset everything**: user loaded a 92mm Bin/Baseplate preset, clicked what they assumed was "the" Factory Reset button, and the base unit stayed at 92mm. Turned out there are 4 separate Factory Reset buttons (Common + one per tab), each scoped only to its own section — the user had clicked Bin's, which doesn't touch Common. Per user request ("Factory reset should do just that — reset all settings to Gridfinity defaults"), linked the two: Bin's/Baseplate's Factory Reset now also resets Common, and Common's Factory Reset now also resets Bin and Baseplate (clearing their active-config selection too, since neither preset's snapshot survives a defaults reset either). Grid Optimizer's Factory Reset stays independent since it doesn't share Common fields — confirmed this scope with the user via AskUserQuestion before implementing, since a "reset everything from any button" interpretation would've meant Optimizer's reset silently discarding Bin/Baseplate/Common too.
- **Grid Optimizer dimensions table made sortable**: click a column header (Description/Width/Depth) to sort, click again to reverse, `▲`/`▼` indicator on the active column. Pure front-end feature — `readOptimizerItemsFromDom()` already reads `items` straight off the DOM in current order for every validate/Calculate/save-config call, so the sorted row order is simply whatever ends up saved, no new persistence format or python-side changes needed. Newly-added rows respect the active sort instead of always appending to the bottom. Bumped `PALETTE_VERSION` (18) since `index.html`'s `<thead>` markup changed.
- **"Document attribute" → "component attribute" terminology fix**: user (with past experience using real Fusion Design-level attributes) asked us to confirm which attribute scope this add-in actually uses, since "stored on the component as a document attribute" sounded contradictory. Confirmed via `generation.py`: `newCmpOcc.component.attributes.add(...)` is `Component.attributes`, not `Design.attributes`/`Document.attributes` — a genuine **component attribute**, attached to the `Component` object itself. Fixed the mislabeling everywhere it appeared: `CLAUDE.md`, `README.md`, `docs/Dev_Notes.md` (the 2026-07-15 entry above), `docs/GGPlus_Help.md`, `docs/GGP_Help_v1.1.0.0.md`, and an `entry.py` code comment. "Stored on the component" itself was already correct — only the attribute-scope label was wrong.

Added a v1.1.0.0 entry to `Archive/!Release_Notes.md` mirroring the README's "What's New" list. ## 2026-07-17 — v1.1.0: grouped Undo, resync-aware preview tracking, config manager + modal redesign, Theme tab font/export/remove
