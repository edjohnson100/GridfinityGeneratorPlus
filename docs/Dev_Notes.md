## 2026-07-15 — Generate now requires Hybrid design intent

- Follows directly from confirming the existing "settings stay with the component as a document attribute" behavior (built in an earlier session, re-discovered/confirmed for the user this session) — the user identified it as the add-in's core value proposition (revisit or share a design months/years later and still be able to edit it) and wanted it *guaranteed*, not just available when the document happens to be in the right mode.
- Scope decision, clarified with the user: only `generate`, not `update_preview`. Considered a proactive "warn on palette open" banner too, but the user pointed out the palette stays open across document tabs — someone could be generating fine in a Hybrid document, switch to a Part/Assembly one mid-session, and a stale one-time-on-open check wouldn't catch that. Checking at Generate time (`entry._ensure_hybrid_design_intent()`, mirroring the existing `_ensure_safe_to_mutate()` shape) handles that correctly with no extra palette state. Preview stays unrestricted since it doesn't produce anything permanent or attribute-bearing — no reason to block someone from previewing in a Part/Assembly document, only from locking in a component that can't carry its own settings.
- Confirmed the failure path doesn't lose any in-progress field values: the check happens before `previewState.clear_preview()`/`generation.create_and_build()` are ever called, and nothing sends a `set_state` back to the palette on this path, so the form is exactly as the user left it — they can switch document tabs and click Generate again with the same entries.

## 2026-07-15 — Theme tab follow-ups: data-theme root-element bug, multi-theme persistence, Edit Active Component crash

- **Theme switching did nothing visually** (built-in themes; import appeared to work but only the dropdown label was actually updating). Root cause: `script.js` set/removed `data-theme` on `document.body`, but every rule in `style.css` is written `:root[data-theme="..."]` — `:root` only ever matches `<html>`, never `<body>`, so no rule could ever match regardless of theme. Fixed both call sites (the system-preference watcher and `applyTheme`) to target `document.documentElement` instead.
- **Imported-but-inactive themes were lost on restart**: the original persistence only remembered the single currently-active theme's `{name, customVars}` in `GGPlus_config.json`, so importing a second theme (making the first inactive) silently dropped the first one's data on the next add-in restart. Added a dedicated `imported_themes.json` (`lib/appConfig.py`'s `load_imported_themes()`/`save_imported_theme()`, `{themeId: varsDict}`) that accumulates every theme ever imported, independent of which one is active — `GGPlus_config.json` now only stores the active theme's *name*, and `get_defaults` sends the full imported-themes dict alongside it so `script.js` can restore the whole dropdown + in-memory cache, not just the active entry.
- **`Edit Active Component` crashed** (`AttributeError: 'Component' object has no attribute 'activate'`) — first real-world test of a feature built earlier this session. `des.rootComponent.activate()` doesn't exist; `.activate()` is an `Occurrence` method (there can be many occurrences of one component, so "activating a component" is ambiguous — confirmed via Autodesk's own API discussion). Returning to the root context is a `Design`-level operation: `Design.activateRootComponent()` (confirmed via official API docs — no params, returns bool). Checked for the same mistake elsewhere in the codebase; this was the only occurrence.

## 2026-07-15 — Theme tab (Theme Designer Pro integration)

- 4th palette tab, hooking in the user's own portable "Theme Designer Pro" theming standard (`Theme_Designer_Pro_Integration_Guide.md`, a generic doc they reuse across projects — confirmed the `ThemeDesigner.html`/`style.css` files it references as "in this repo" don't actually exist here, it's boilerplate from wherever they normally drop it, not something authored for this repo specifically). Standard is plain CSS custom properties + a `data-theme` attribute, no dependencies.
- Rewrote `resources/palette/style.css` from ~6 ad hoc variables (`--bg`, `--fg`, `--border`, `--accent`, `--error`, `--success`) plus a `@media (prefers-color-scheme: dark)` block, to the full ~25-variable Theme Designer Pro set (plus a few project-specific `--banner-warning-*` vars for the edit banner, which isn't part of the standard 25). `:root` reproduces the exact previous default look; `:root[data-theme="Dark"]` reproduces the exact previous dark-mode look (formalized from the old media query, including fixing a gap where `.notification` was never actually dark-styled before). Added two new built-in themes designed for this session — "Midnight" (deep navy-blue dark variant) and "Sandstone" (warm amber-accented light variant) — since the user asked for 1-2 extra options beyond Light/Dark, left to my judgment.
- Preserved the old automatic-OS-dark-mode behavior as an explicit "System" option (the new default) rather than dropping it outright when moving to an explicit theme picker — `script.js` watches `matchMedia('(prefers-color-scheme: dark)')` and toggles `data-theme="Dark"` live only while "System" is selected.
- Supports importing a `.theme.json` (the standard's `{id, vars}` export shape) via a plain `<input type="file">` + `FileReader`, entirely client-side — no Python involvement in reading the file, confirming with the guide's own Step 5 that this needs no build step or library.
- Persistence: reused the exact `lib/appConfig.py`/`GGPlus_config.json` mechanism already built for palette window geometry, rather than the `DEFAULTS_BY_TAB`/named-preset system the other tabs use — a single ambient "current theme" value has no need for save/load/delete of multiple named variants. New `update_theme` action in `entry.py`, sent immediately on every selection/import (no explicit "save" step, matching how a theme picker should feel). `onSetState` in `script.js` special-cases `tab === 'theme'` to skip the generic validate/render pipeline (there's nothing to validate) and call `applyTheme()` instead.

## 2026-07-15 — Preview components visually marked as unfinalized

- User asked about reusing a "ghost body" technique from their other add-in, FingerJointsLive, to make preview components visually distinct from finalized ones (plus a "PREVIEW_" name-prefix idea). Investigated FingerJointsLive first rather than assuming the same technique would transfer: it draws a temporary `CustomGraphicsGroup` overlay (translucent faces + wireframe edges) on top of geometry that doesn't exist as a real body yet (proposed cut tools). That doesn't fit here, since `generation.create_and_build()` always builds *real* geometry — preview vs. final only differs in whether it's tracked for possible deletion. For an already-real, not-yet-finalized component, `Component.opacity` (confirmed via Autodesk's official docs) is the better-fitting native mechanism — it's the same property Fusion itself uses to auto-ghost inactive components during in-context editing, and it's set once per component regardless of how many bodies it contains (relevant now that Stackable baseplates can be multi-body).
- Implemented as `generation.create_and_build(kind, form, is_preview=False)` — when `True` (only `_handle_update_preview` passes this), the built component gets a `PREVIEW_` name prefix and (initially) `Component.opacity = 0.4`. `_handle_generate` passes nothing, so Generated components are unaffected (plain name).
- Confirmed with the user this should also apply to re-editing an already-generated component via "Edit Active Component" — not just fresh previews. That meant `previewState.py` needed real new scope, not just cosmetics: `track_preview()` gained an `original_name` param, and `clear_preview(force=False)` (the "release tracking, leave the component alone" path used by `PaletteCloseHandler`, add-in `stop()`, and switching to edit a different component) now restores it — so a real, permanent component being edited is never left permanently prefixed if the user closes the palette or Fusion mid-edit without clicking Update Preview/Generate/Clear Preview. Traced the existing lifecycle first to confirm this was the *only* place needing new logic: "Update Preview" while re-editing already works by deleting the old real component (`force=True` always deletes an adopted component too) and building a fresh one, which then flows through the same fresh-preview marking path — no special-casing needed for that transition.
- **Follow-up**: the user tested in Fusion and `Component.opacity` had no visible effect on the preview body at all (screenshot showed a fully-opaque preview bin). Rather than debug why (root-component opacity inheritance quirks are a known Fusion API gotcha, but not worth chasing for a cosmetic nice-to-have), removed opacity entirely per the user's call — `PREVIEW_OPACITY` constant, the `original_opacity` plumbing through `track_preview`/`clear_preview`, and both `.opacity` assignment sites all deleted. The `PREVIEW_` name prefix alone was judged sufficient.

## 2026-07-15 — Grid Optimizer tab; Stackable baseplate type; palette bug fixes

- **Grid Optimizer tab** (`commandGridfinityPalette/optimizer.py`, `optimizerInputState.py`): new third palette tab, a pure-Python advisory calculator (no `adsk.fusion` geometry) that recommends a custom Gridfinity grid pitch for a user-entered list of drawer/cabinet openings. Ported from a standalone reference script the user had been running manually. `run_optimization` ranks candidate grid sizes by a priority-weighted score (`widthOnly`/`width`/`depth`/`depthOnly`/`balanced`) while still reporting the actual unweighted leftover mm for display. Half-bin credit is an explicit user-facing toggle (not baked in silently) since the user found it materially changes the recommended size. The dimension list uses the same named-preset save/load/delete system Bin/Baseplate already had (`DEFAULTS_BY_TAB`/`VALIDATE_BY_TAB` extended to include `optimizer`) rather than a bespoke auto-persist file, per explicit user request to match "the config options."
- **Bin/Baseplate presets now snapshot the Common panel**: previously, saved presets always stripped `COMMON_FIELDS` (base unit, XY clearance, magnet size) so loading a preset never touched the shared panel — surprising to the user, who expected a preset to reproduce the exact grid it was designed for. Added `TABS_WITH_SHARED_COMMON = ('bin', 'baseplate')` in `entry.py`: presets for these two tabs now keep the Common fields and restore them (updating the one shared `common.json`) on load; Optimizer presets still strip them, since dimension lists have no relationship to the physical grid.
- **Stackable baseplate type** (`lib/gridfinityUtils/baseplateGenerator.py`): 4th `plateType` option, built like Light under the hood (no magnet cutouts/screw holes/extra bottom). Technique specified directly by the user from real 3D-printing experience: split the Light-style body exactly at its mid-height, **remove** (via `features.removeFeatures.add()` — a genuine non-destructive Fusion "Remove" timeline feature, distinct from Delete, confirmed via Autodesk's official API sample) the discarded bottom half, mirror the retained top half across the same plane, and rejoin — producing a top/bottom-symmetric plate with no stacking overhang, while preserving total height (verified algebraically). When Stack Count > 1, an interface-layer spacer is extruded directly from the plate's real top face (`faceUtils.getTopFace` — confirmed via a user screenshot that a plain rectangular box was wrong; the profile must match the actual lattice/webbing shape between grid cavities, corners included) and both bodies are Z-patterned with matching spacing via a new `patternUtils.linearPattern` helper (the existing `recPattern` was hardwired to two directions). Follow-up refinements: patterned bodies are explicitly renamed post-pattern (`Baseplate_01`, `Baseplate_02`, ... / `Interface_01`, `Interface_02`, ...) rather than left to Fusion's own auto-numbering, which the user noted doesn't reset predictably and can produce names like `Baseplate(482)`; interface layers get a contrasting duplicated appearance (`design.appearances.addByCopy` + `ColorProperty`) applied to the seed body only, so pattern copies inherit it automatically.
- **Validation cm/mm bug** (`validation.py`): found via a user report that editing Common's XY clearance always errored, and the error message's own suggested range (`[0.01, 0.05]mm`) always failed. Root cause, systemic across `validate_bin`/`validate_baseplate`: any field that's mm↔cm-converted for display (per `MM_FIELDS` in `script.js`) arrives at Python validation already in centimeters, but several bound literals/messages were written as if checking millimeters directly — off by 10x. Fixed all seven affected messages (pure text correction, enforced numeric thresholds unchanged, since current defaults already satisfy them).
- **Input clobbered mid-typing**: the reported "value forced to an integer" turned out to be a second, related bug — only the Common panel eagerly round-trips every edit (`update_common` → Python saves → `set_state` pushes the reloaded value back → `writeFormToDom` rewrites the DOM), and a mid-typing round-trip could overwrite the field the user was still editing. Fixed by skipping the currently-focused element in `writeFormToDom` (`script.js`).

## 2026-07-14 — Collapsible sections; re-edit/redo/delete a previously generated component

- **Collapsible sections**: converted each `<fieldset>`/`<legend>` group inside the Bin and Baseplate tabs (`resources/palette/index.html`) to native `<details class="section" open>`/`<summary>` — all expanded by default (per user request), user-collapsible per section, no JS needed since browsers handle the disclosure natively. IDs some sections needed for conditional-visibility JS (`bin-compartments-fieldset`, `baseplate-magnet-cutouts-fieldset`, `baseplate-screw-holes-fieldset`) were preserved on the `<details>` element, so no `script.js` changes were required. The "Common settings" panel (outside the tabs) was left as a plain `<fieldset>`.
- **Re-edit a previously generated component** ("redo"/"delete" without manual Fusion UI): raised in the user's weekly Fusion Zoom meeting — once a bin/baseplate is Generated it becomes a normal permanent component with no link back to the add-in, so fixing a mistake meant manually deleting/editing in the Fusion timeline. Implemented by reusing the existing preview machinery rather than adding new deletion logic:
  - `generation.create_and_build()` now stamps every Hybrid-design-intent component it builds with custom attributes (group = `config.ADDIN_NAME`): `kind` (`bin`/`baseplate`) and `formJson` (the exact cm-unit form dict used to build it). Runs for both preview and Generate calls — harmless for previews, gives every permanent component a durable record of its own parameters.
  - `previewState.py` gained an `adopted` flag (`track_preview(tab, tracked, adopted=False)`) and a `force` param on `clear_preview(force=True)`. A fresh preview is always deleted on clear; an *adopted* component (see below) is only deleted when `force=True` (an explicit Clear Preview / Update Preview / Generate click) — implicit paths (`PaletteCloseHandler`, add-in `stop()`) now call `clear_preview(force=False)`, which just releases tracking and leaves the real component alone. This was a deliberate safety call: closing the palette mid-edit must never silently delete a user's real generated part.
  - New palette action `edit_active_component`, wired to a new top-level "Edit Active Component" button (not tied to either tab). Per the user's explicit preference, this reads Fusion's `Design.activeComponent` (the user activates the target component in the browser — hover over its name and click the radio button that appears to its right — first) rather than tracking a live viewport/browser *selection* — more stable, no new `SelectionCommandInput`/command needed. `entry._handle_edit_active_component()` reads back the `kind`/`formJson` attributes, resolves the owning `Occurrence` via `rootComponent.allOccurrencesByComponent(comp)`, reactivates root, and adopts the occurrence into `previewState` — after which the existing Update Preview (rebuild in place) / Generate (make permanent again) / Clear Preview (delete) flows all "just work" against it unmodified.
  - Scope: Hybrid design intent only (the only mode where `generate` creates a single owning `Occurrence`/`Component` to tag and re-adopt) — Part/Assembly-intent builds (loose root-component features, no owning entity) are explicitly out of scope, confirmed acceptable with the user.
  - UI: a persistent per-tab "editing" banner (`resources/palette/script.js`/`style.css`, distinct from the auto-hiding `#notification`) shows the component name and available actions while an adopted edit is in progress; cleared on `preview_status` inactive or once a fresh (non-adopted) preview replaces it.

## 2026-07-14 — Palette config manager, Common settings panel, Clear Preview, GitHub setup

- **Config manager**: added full save/update/load/delete for named configs per tab (Bin/Baseplate), plus per-tab Factory Reset, in the palette UI (`commandGridfinityPalette/entry.py`, `resources/palette/script.js`, `index.html`). Backed by file-per-config JSON in `commandConfig/presets/{tab}/*.json` and `ui_defaults.json` (`activeConfig` per tab).
  - Fixed a `KeyError` where the new config `<select>` was mistakenly caught by the generic field-change listener (`#tab-bin input, #tab-bin select`) and treated as a form field, triggering backend validation for a tab named `bin-config-select`. Fix: scoped the listener to `[id^="bin."]` / `[id^="baseplate."]`.
- **Common settings panel**: `baseWidthUnit`, `baseLengthUnit`, `xyClearance`, `magnetDiameter`, `magnetDepth` were duplicated across Bin and Baseplate configs with no way to keep them in sync. Pulled them into a single always-visible "Common settings" panel above the tabs, backed by `commandConfig/common.json` and a `common`/`update_common` action pair mirroring the per-tab pattern.
  - Design call: kept `hasMagnetCutouts` (the on/off toggle) **per-tab** rather than folding it into Common, because Light-baseplate-type gating needs to disable baseplate's toggle independently of bin's. Only the physical magnet size moved to Common.
  - Saved named presets never include the Common fields — they're stripped before dumping (`COMMON_FIELDS` filter in `_handle_save_as`/`_handle_update_current`).
- **Light baseplate type gating**: user reported editing "Extra bottom thickness" and "Add connection holes" had no visible effect on Light baseplates. Root cause: intentional existing gating in `baseplateGenerator.py` (`hasExtendedBottom`/`hasSkeletonizedBottom`), not a bug — the UI just didn't communicate it. Fix was UI-only: disable + hint text, generator logic untouched. Extended the same treatment to magnet cutouts and screw holes when `plateType === 'Light'`, since those are gated the same way.
- **Clear Preview button**: previously, canceling after "Update Preview" left a temporary preview component in the design with no clean way to remove it short of manually deleting it in the Fusion timeline. Added a third button per tab wired to the existing (already-correct) `previewState.clear_preview()`; the palette's `preview_status` message (previously an inert no-op in `script.js`) now enables/disables the button based on whether a preview is currently tracked.
- **Debounce bug fix (found incidentally)**: `script.js` used a single shared `validateDebounceTimer` for all tabs' field validation. Two `requestValidation()` calls for different tabs within the same 200ms window would cancel each other via `clearTimeout`, silently skipping validation for one tab. This became more likely once Common-panel edits started firing `requestValidation('bin')` and `requestValidation('baseplate')` back to back. Fixed by keying the debounce timers per tab (`validateDebounceTimers`).
- **GitHub**: repo initialized and pushed as a private repo at `github.com/edjohnson100/GridfinityGeneratorPlus` (`main` branch). `.gitignore` had been ignoring `CLAUDE.md` (likely copied from a template that treats it as personal/local) — removed that line so `CLAUDE.md` is tracked, since it's genuine project documentation.
